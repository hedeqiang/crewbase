# 参考笔记：常驻 Agent 与 Super-agent

两篇文章（2026-11-15 调研）：

- Anthropic，[Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)：常驻 Agent 的五个基础件——事件收件箱、定时器、记忆、权限、发件箱。
- DeepSeek Harness 团队，《Super-agent 设计探索：迈向更自主的 Agent 系统》（微信公众号）：连续、高效、主动、持久四个特征；双层架构（Router + Worker）、事件驱动、全双工交互、存算分离、Watchdog。

两篇的共同判断：Agent 循环本身没变，变的是外围——什么时候醒、醒来带什么上下文、跑完怎么交付、出了问题谁来兜底。单任务的上限取决于模型，多任务的上限取决于人的注意力；系统应当接管会话管理，让人只做决策与验收。

## 要点

### Anthropic：五个基础件

| 基础件 | 要点 |
|---|---|
| 事件收件箱 | 所有触发（消息、Webhook、定时、后台任务）先写入持久表，按来源 ID 去重，记录状态；收件箱是唯一事实来源，进程崩溃后可重试；每个收件箱同一时间只有一个 worker；连续多条消息合并成一次运行，只回复一次；运行中来新事件可选：排队 / 并入当前运行 / 打断重来 |
| 定时器 | 跟进（Agent 给自己设的提醒，如「两小时后看对方回了没」）与周期任务分开存；调度器轮询到期定时器，写入收件箱，而不是直接启动运行 |
| 记忆 | 只存查不回来的东西（其他系统里有的只存指针）；用户指令每次运行都加载；用户笔记先索引后按需读；记录「已经告诉过用户什么」避免重复；每个进行中的任务一份进度文件；可选「做梦」：离线整理记忆、淘汰过时条目、发现跨会话规律；常驻开销要精简并利用提示缓存 |
| 权限 | 凭证由环境外的代理注入，Agent 不持有密钥；高风险操作由分类器把关；**延迟工具调用**：需要审批时运行结束、会话保存在调用处，用户的回答作为新事件进入收件箱，开新运行接着做，等待期间 worker 可处理别的事 |
| 发件箱 | 后台工作只交付结果和关键细节；一次运行以三种方式结束：发消息 / 判断无需打扰 / 发起延迟调用；先安静，再逐步赢得注意力；用评测校准消息量 |

### DeepSeek：Super-agent

| 模块 | 要点 |
|---|---|
| 双层架构 | 常驻 **Router** 承接所有人机交互与全局协调，不亲自干活（可以不给 bash），轻量模型即可；**Worker** 上下文隔离、并发执行具体任务，用最强模型，不直接对外说话，向 Router 汇报。Session 是实现细节，不应成为用户的认知负担 |
| 批处理 | Router 推理期间积压的事件在下一轮一并注入；长输入短输出，合并的边际成本低（实验：每分钟 1→40 条，平均批大小 1.0→2.8，单个决定分摊耗时 6.4s→1.6s） |
| 事件过滤 | 两级：程序规则（来源、群范围、白名单：只响应明确请求 / 作为候选 / 忽略）做 Fast Path，大模型按提示词策略做 Slow Path |
| 订阅与直通 | 同一 IM 话题 / PR / 邮件串构成 Thread；Worker 订阅 Thread 后，后续事件由程序直接送达，不经 Router（实验：Router 决定数 −30%，token −37%） |
| 上下文 | Inline & Spill：先给 ID 与摘要，按局部性内联相邻内容，超长截断并留续读入口；**链式召回**：各对象有 ID 且互相内联引用，模型可沿引用逐跳展开 |
| 提前行动 | 投机执行：讨论还在进行时后台先复现、查资料、拟草稿；有价值才交付，否则保持安静（「静默复现并修复」） |
| 全双工 | 耗时命令与子任务改为异步 start / stop，立即返回「已启动」，完成后结果作为新事件进入会话；期间照常响应人 |
| 多信道 | IM 低打扰、只在需要决策或验收时说话，单次回复不超过 100 词；GitHub / 邮件等异步信道给结构化完整交付 |
| 存算分离 | 计算无状态、会话状态持久化；执行环境留在原地，端侧轻量 daemon 只执行命令（BYOM），设备重新上线后补做任务 |
| Watchdog | 主系统之外的独立会话，定时驱动：既管基础设施故障，也由模型判断各 Worker 是否有实质进展、是否偏离目标；可以用自然语言问它、让它调整提示词与触发规则 |

## 对照 Crewbase

| 能力 | 现状 | 差距 |
|---|---|---|
| 收件箱 | 每个 Agent 一个 FIFO 队列，写入会话日志，重启后恢复未领取的输入；Webhook、例行巡检、晨报 | **已领取但未跑完**的输入在重启后丢失；连续多条消息逐条各跑一轮；运行中来消息只能排队，不能并入当前运行；来源 ID 去重仅 IM 部分有 |
| 定时器 | Cron 例行巡检、晨报、持久目标续跑 | Agent 不能**给自己设跟进**（「明早 9 点检查 CI」） |
| 记忆 | INSTRUCTIONS.md、MEMORY.md + SQLite 全文、history_search / history_read、压缩 | 没有「已告知用户」记录、任务进度文件、离线整理（做梦） |
| 权限 | 三档运行模式、规则引擎、审批、钥匙串凭证、脱敏、审计 | 审批是**阻塞式**：等待期间整个 Agent 卡住，守护进程重启后待审批的调用丢失 |
| 发件箱 | notify（桌面、手机、IM）、免打扰、晨报 | 没有按信道的输出规范（IM 简短）；没有「判断无需打扰」的显式收尾 |
| 双层架构 | 频道单一负责人 + 委派子 Agent + 任务板 | 没有常驻「主理人」统一接待、分派、汇报；用户要自己挑 Agent、管会话 |
| 事件过滤 / 订阅 | IM 网关：@ 提及与已绑定话题 | 群聊旁听（不 @ 也判断要不要管）、Thread 订阅直通 |
| 全双工 | 长命令同步执行，期间不响应 | 后台命令（start / 查看输出 / stop），完成后作为事件回到会话 |
| Watchdog | 持久目标有「无进展」检测 | 通用的卡死 / 原地打转检测与自动处置 |
| 存算分离 | 中继、服务端 Profile | 云端 Agent + 本机执行 daemon（BYOM）——暂不做 |

## 吸纳计划

按「打磨 bot 本身」的优先级排进迭代 17–19（见 TODO.md）：先做每天都会碰到的（合并消息、运行中插话、给自己设跟进、后台命令、卡死检测、信道规范），再做可靠性（重启续跑、非阻塞审批、记忆结构），最后做「主理人」双层架构与群聊旁听。存算分离 / BYOM 与 A2A 暂不做。
