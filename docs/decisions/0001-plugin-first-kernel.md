# ADR-0001：采用插件优先的内核

- 状态：提议
- 日期：2026-11-14

## 背景

最直接的做法，是把多模型路由、沙箱、审批、Routines、IM 网关设计成守护进程内的固定模块。这会带来三个问题：

1. 社区要增加一个沙箱后端、模型提供方或 IM 网关，必须修改内核代码并等待我们发版。
2. 审批、规则、审计、脱敏等横切逻辑与工具执行耦合，每加一种策略都要改执行路径。
3. 桌面版、服务器版、ACP 服务器版需要不同的模块组合，只能靠编译开关或条件分支。

DeepSeek Harness（MIT）用 Cordis 实现了「一切皆插件」：没有特权内核，Agent 循环本身也是插件；能力拆为定义 / 提供方 / 消费方；工具执行流水线通过 waterfall 事件开放拦截点；运行形态由 Profile 和补丁组装。其文档详细，且已在 Web、Headless、SDK、ACP 多种形态上验证。

## 决策

1. Crewbase 采用插件优先的内核：只有插件宿主（服务注册表、类型化事件、副作用跟踪、依赖解析、Profile 加载、进程外桥接）不可替换，其余全部是插件。
2. 移植 Cordis 的核心概念（插件、上下文、依赖注入、五种分发模式、可撤销副作用）和 Harness 的架构约定（能力 seam、作用域、会话日志唯一真源、工具执行流水线、Profile 与补丁、远程方法白名单、界面插槽）。
3. 用 Go 重新实现，而不是直接基于 Harness（TypeScript）开发。

## 考虑过的方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 固定模块 | 实现最直接 | 扩展性差；与 PRD「社区共建生态」目标冲突 |
| B. 直接 fork Harness（TypeScript） | 现成的大量子系统；与其插件生态兼容 | 常驻 Node 进程内存高；与 PRD 的 Go / 单文件分发冲突；Harness 处于开发者预览，频繁破坏性变更；我们的多 Agent 频道模型需大幅改动其以会话为中心的设计 |
| C. 在 Go 中移植其设计思想（选定） | 单文件分发、低内存、适合管理大量子进程；保留 Harness 架构的优点；产品模型由我们主导 | 需要自己实现内核与核心插件；Go 不适合进程内热加载（由 ADR-0002 解决） |
| D. Go 守护进程 + 内嵌 Harness 作为子系统 | 复用其工具与子系统 | 两套插件模型并存，调试与安全边界复杂 |

## 后果

- **正面**：第三方可以不改内核就扩展任何能力；同一套插件组装出桌面、服务器、ACP、SDK 多种形态；无损模型切换、审计、fork 都建立在会话日志之上。
- **负面**：Phase 1 前两周需要投入在插件宿主上，功能可见进度会慢一些；团队需要学习「注册即副作用」「Waterfall 必须调用 next」等约定。
- **缓解**：Phase 0 用 Harness 教程第 7 章的等价示例验证宿主；CI 加入 `crew lint plugins` 检查未登记的副作用；文档提供概念对照表帮助熟悉 Harness 的贡献者上手。
- **互通**：通过 `subagent-acp` 提供方，Crewbase 可以把一个轮次委派给 Harness 的 ACP profile，反之亦然。
